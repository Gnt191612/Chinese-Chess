# 控制逻辑与规则审计

审计日期：2026-10-03。首次审计记录如下；后续修复状态见文末。

## 已复现

1. 选择黑方后仍设置玩家回合。`GameLogic::Initialize`固定设置`m_playerTurn=true`，使红方AI无法先行；当前主界面默认红方，因此通常未触发。
2. `ChessBoard::MovePiece`未检查`m_gameOver`。测试设置结束状态后，接口仍接受红兵前进。当前UI有结束检查，内部接口缺少终局保护。
3. `GameLogic::AIPlay`不检查`MovePiece`返回值，提前记录经验并无条件切回玩家回合。注入一着非法黑车斜走后，棋盘拒绝着法，但界面显示玩家回合而棋盘仍为黑方，造成无法正常继续的状态。

## 静态检查发现

- `main.cpp`以红方是否被将死判断赢家。红方困毙时`IsCheckmate(RED_P)`为假，界面会显示红方获胜；应依据无合法着的当前方判负。
- 缺少对局局面历史与重复局面、长将、长捉和自然限着的裁决。不能宣称实现完整比赛规则。
- AI返回时未比对当前棋盘哈希与开始搜索时的哈希。正常鼠标流程在思考期间禁止走棋，重新开局也等待并丢弃旧结果，但公开可修改棋盘接口可能导致快照过期。
- `GetBestMove`在搜索开始后重置停止标记。若取消请求恰好发生在初始化阶段，可能被清除，重新开局等待时间可能接近搜索上限；当前取消测试仅覆盖搜索已经运行后的情况。
- 静态搜索深度耗尽时，在被将军局面直接返回静态评价，可能低估强制应将和杀棋。这是评价错误风险，现有根节点合法着过滤仍会阻止实际非法落子。

## 已验证

- 正常初始局面生成44个合法着。
- 开局全部44着均能通过正式移动接口。
- 这44着搜索走棋与撤销后恢复原始哈希和当前方。
- 移走将帅之间唯一遮挡子的着法被拒绝。
- 静态检查确认马腿、象眼、炮架、九宫、象不过河、兵卒方向与过河横走均有对应条件。

复现及回归测试：`tests/RulesAudit.cpp`，非零退出表示问题仍存在。

## 修复顺序建议

先修复AI落子成功判断和回合一致性，再修复终局保护、黑方开局与困毙显示，随后加入快照校验和可靠取消。完整比赛裁决应明确规则版本后单独实现。训练前应先完成这些控制层修复。
